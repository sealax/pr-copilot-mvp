## 2. What Is Working

- Basic Next.js Pages Router app.
- GitHub login and logout via Supabase OAuth exist in `pages/index.tsx`.
- Server-side Supabase auth is enforced in `/api/evaluate`, `/api/generate`, and `/api/usage`.
- API routes verify the user from the Supabase bearer token and no longer trust client-supplied user identity.
- OpenAI-backed PR readiness evaluation works.
- Evaluation returns structured verdict, risk, recommendation, journalist reaction, and next-action data.
- Evaluation output is clamped and normalized before persistence.
- New evaluations are saved to Supabase without persisting the raw model payload.
- Generation requires a saved evaluation ID owned by the verified user.
- NO-GO generation is blocked client-side and server-side.
- Free usage tracking is database-backed via the `generations` table.
- Basic API rate limiting and input length validation exist.
- Logged-in users can fetch recent evaluations.
- Clicking a recent evaluation loads its saved structured evaluation data and tries to load the latest linked generation.
- `npm run build` passes.

## 3. Incomplete Or Fragile

- UI is very basic and mostly inline-styled.
- Login is minimal: there is logout, but no full account area or protected dashboard.
- History only fetches the latest 5 evaluations.
- Clicking a recent evaluation can log an expected "no generation found" state as an error.
- Evaluation and generation APIs still use `any` and untyped request handlers in places.
- No schema validation library.
- No lint script.
- No tests.
- No Stripe/payment logic yet.
- No real production onboarding or pricing state.
- Supabase database schema and RLS policy setup are not documented in the repo.
- Some unused frontend code remains, including text-parsing helpers from earlier evaluation output.

## 4. Remaining Security And Production Risks

- RLS policies for `evaluations` and `generations` still need to be documented and verified outside this repo.
- In-memory rate limiting is useful for MVP abuse protection but is not durable across serverless instances.
- Free usage enforcement depends on counting saved `generations` rows; production billing will need a stronger entitlement model.
- API routes should be typed and ideally backed by explicit schema validation.
- Error handling is functional but still MVP-level.
- OpenAI, Supabase, and OAuth production environment settings must be verified before public deployment.

## 5. Usage Tracking

Usage tracking is now database-backed.

- `/api/usage` verifies the Supabase bearer token.
- Usage is counted from rows in the `generations` table for the verified user.
- `/api/generate` enforces the free generation limit server-side before calling OpenAI.
- The frontend displays remaining free generations based on `/api/usage` and generation responses.

This replaces the older local React-state-only usage tracking and is no longer reset by refreshes or direct API calls.
